## Context

After slice 4, an app is created from a public `https://github.com/<owner>/<repo>` URL and deploys on creation and on Redeploy. The service (`tero serve`, `tero.service`) queues a deploy row; the agent (`tero agent`, a user unit under `tero`'s user manager, listening on nothing) claims it, clones the branch head with go-git, builds and starts it. The two share state only through `tero`'s SQLite database at `/var/lib/tero/tero.db`. Builds run one at a time per server, and an app with a deploy queued, building or starting refuses Redeploy.

`tero-keys` holds the master key, the admin's credentials, sessions, passkeys and the security log. It has no network, answers only the dashboard (by its exact system cgroup) and root, and seals values with AES-256-GCM under the master key. It can't answer the agent: `tero`'s user manager delegates its cgroup subtree to `tero`, so anything running as `tero` can join the agent's cgroup, and the agent shares its uid with the internet-facing dashboard.

GitHub facts that shape the design:

- The App manifest flow creates an App from a JSON manifest the admin approves on github.com, for a personal account (`https://github.com/settings/apps/new`) or an organization (`https://github.com/organizations/<org>/settings/apps/new`, by an owner). GitHub then redirects to Tero with a one-time `code` (valid for an hour), and `POST /app-manifests/{code}/conversions` returns the App's id, slug, owner, private key (PEM) and webhook secret. No credential is needed for the conversion.
- A private App (`public: false`) can only be installed on the account that owns it, so one App means one installation.
- An App authenticates with a JWT it signs with its private key (RS256, at most 10 minutes). With it, Tero mints installation tokens that last an hour and can be narrowed to some repositories and permissions; `DELETE /installation/token` revokes one early.
- Webhooks carry `X-Hub-Signature-256`, an HMAC-SHA256 of the raw body with the webhook secret, and `X-GitHub-Delivery`, a unique id. GitHub doesn't redeliver a failed delivery on its own; it keeps an App's deliveries for 3 days and redelivers one when asked through the API.
- Commits pushed to a fork can be fetched by SHA through the parent repository, so a SHA taken from a webhook proves nothing about the branch.
- The dashboard's cookies are `SameSite=Strict`: GitHub's redirect back to Tero is a cross-site navigation and arrives without them, but requests the landed page makes to its own origin carry them.

## Goals / Non-Goals

**Goals:**
- A push to an app's tracked branch deploys it, from a private or public repository, without the admin opening the dashboard.
- The internet-facing dashboard never holds a GitHub credential: not the App's private key, not a JWT, not an installation token. A compromised dashboard can't read private code.
- The agent runs under its own uid, so `tero-keys` can tell it apart from the dashboard and anything else, which slice 6 builds on to hand it app secrets.
- Every repository token is scoped to one repository, read-only, held only in the agent's memory and revoked after use.
- Nothing a webhook says can make Tero build a commit that isn't the head of the tracked branch on GitHub.
- A push made while the server was down deploys once it is back.

**Non-Goals:**
- More than one GitHub account per server, GitLab, Bitbucket or any other forge.
- Preview deploys for pull requests (after v1) and waiting for CI checks before deploying.
- Commit statuses or deployment events written back to GitHub; the App asks only for read permissions.
- App secrets and the rule for which sources `tero-keys` releases them to (slice 6). This slice gives the agent its identity and its one verb, `github.jwt`.
- Deploy history beyond what the app page shows, and rollback (slice 7).
- Visual design of the new settings and form parts, which stay plain markup.

## Decisions

### The agent under its own user

- **A `tero-agent` system user.** Init creates `tero-agent` with no login shell, home `/var/lib/tero-agent` (mode 0700; Podman 4.9 makes it 0711 so container processes can reach their storage, which still lets nobody list or read it), lingering, and the 1,000,000-id subordinate range that `tero` held. Rootless Podman, its storage and configuration, BuildKit's cache volume, the build working directories and every app container move to it. The agent's unit stays in `/etc/systemd/user/`, owned by root, now with `ConditionUser=tero-agent`. `tero` loses its subordinate range, lingering and user manager: the dashboard is a system service and never needed them. `tero.service`'s `InaccessiblePaths=` for Podman's directories goes away, since the dashboard can't enter `tero-agent`'s home at all.
- **Nothing else runs as `tero-agent`.** Its user manager runs the agent and the `systemd-run --user --scope` units holding each container's conmon and port forwarder. Container processes never run as `tero-agent`'s own uid: BuildKit keeps its fixed slice (`--uidmap 0:800001:200000`) and apps keep `--userns=auto`, and neither maps the user's own uid. The agent refuses to start a container whose options would map it.
- **`tero-keys` knows the agent by uid.** It reads the peer's uid with `SO_PEERCRED`, as it already does, and treats `tero-agent`'s uid as the caller `agent`, whatever its cgroup. Everything running as that uid is the agent's own code or Podman's helpers it started, so a cgroup check would add nothing. The dashboard is still recognised by its exact system cgroup and uid `tero`; a process running as `tero` outside it is still refused. The socket's group becomes `tero-keys-callers`, holding `tero` and `tero-agent`.
- **The shared state moves to its own directory.** The database and build logs move to `/var/lib/tero-shared/` (`root:tero-shared`, mode 2770, so new files keep the group), with `tero` and `tero-agent` in `tero-shared`. `tero.db` and its WAL and shared-memory files are 0660; build logs are written 0640 by the agent. Caddy's storage stays in `tero`'s home, out of the agent's reach. The database is still the only channel between the two, and the agent still treats every row as untrusted.

### Connecting GitHub

- **One private App per server, created by the manifest flow.** The settings page gets a GitHub section with **Connect GitHub**, which asks whether the App belongs to the admin's personal account or to an organization, by name. The dashboard posts a form to the matching GitHub page with the manifest and a `state`. The manifest asks for `contents: read` and `metadata: read`, the `push` event, `public: false`, the webhook URL `https://<dashboard-domain>/api/github/webhook`, and `redirect_url` and `setup_url` on the dashboard. The suggested name is `Tero <dashboard-domain>`, cut to GitHub's 34 characters; the admin can change it on GitHub before creating it, since App names are unique across GitHub. For an organization the admin must be one of its owners, which GitHub checks.
- **The callback is a page, not an API.** GitHub redirects to `/github/connected?code=…&state=…`, which arrives without the session cookie. The page then posts `code` and `state` to `/api/github/connect`, which does carry it.
- **The state is checked by `tero-keys`.** `github.connect.begin` needs a confirmed session, as in slice 4, because connecting grants the server read access to the admin's code. It returns a `state` of 32 random bytes tied to that session, valid 10 minutes. On the callback the dashboard sends `github.connect.approve` with the state and the same live session (no 5-minute window needed, since creating and installing the App on GitHub can take longer), and `tero-keys` marks it approved. Nobody outside can make the server adopt an App they created. A compromised dashboard, which holds the admin's session while the admin connects, could still swap in a code for its own App; the settings page shows the App's name and owner before the admin installs it.
- **The agent converts, `tero-keys` keeps, the dashboard never sees the key.** The dashboard writes the `code` and the approved `state` to a `github_requests` row. The agent, which polls the database every second, calls the conversion endpoint and sends the App id, slug, owner, private key and webhook secret straight to `tero-keys` in `github.connect` with the state. `tero-keys` accepts them only for an approved state it hasn't used, and seals both secrets under the master key in a `github_app` row. The client secret isn't used or stored. The dashboard's page waits for the request row to be answered (a few seconds) and then sends the admin to `https://github.com/apps/<slug>/installations/new`.
- **Installation.** GitHub redirects to the `setup_url` after the install. Tero ignores the `installation_id` in that URL: the dashboard writes a `refresh_installation` request, and the agent asks `GET /app/installations` with a JWT, which for a private App returns the one installation. The agent stores the installation id and its repositories (id, owner, name, private or not, default branch) in the database. It refreshes them on start, on `installation` and `installation_repositories` webhooks, and when the new-app form asks. A suspended installation is shown as such in settings; a deleted one leaves the App connected but not installed, with the link to install it.

### Only the agent talks to GitHub

- **`github.jwt` answers only the agent.** It returns an App JWT with `iat` 60 seconds in the past and `exp` 5 minutes ahead, signed with `crypto/rsa` over a fixed header, so no JWT library is added to `tero-keys`. The agent uses it for the conversion's follow-ups, the installation, repository lists, branch lookups for private repositories, installation tokens and redelivery. The dashboard has no verb that yields a JWT or token, so a compromised dashboard can't read private code; what it can still do is queue deploys of the apps that exist, as today.
- **Two ways into the new-app form.** A public URL deploys in one step with nothing connected, as in slice 2: no App, no JWT, no token, and polling picks up new commits. Below it, the repositories the App covers, or a "Connect GitHub" prompt when nothing is connected. The JWT and tokens never appear in the interface, and "installing" the App is only GitHub's page for choosing repositories; nothing runs on the admin's machine. Wording to settle with Cele: the error for a private URL without the App (pointing to Connect GitHub), a public repository the App covers switching to deploys on push by itself, and the hint that connecting means deploys on push instead of within a minute.
- **Lookups for the new-app form.** The form lists the installation's repositories from the database. When the admin picks one, the branch is filled from the stored default branch. On create, the branch and folder of a covered repository are checked by a `check_source` request the agent answers within a couple of seconds; the dashboard waits up to 15 seconds and then says to try again. A URL whose owner and name the installation covers takes the same path. Public repositories outside the installation keep slice 2's lookups from the dashboard, which need no credential.
- **Repository tokens are scoped, in memory and revoked.** For each fetch of a covered repository, the agent asks `tero-keys` for a JWT, mints a token with `repository_ids: [<the app's repo>]` and `permissions: {contents: read}`, clones with it as go-git's basic auth (`x-access-token`, never in a URL or in `.git/config`), and revokes it with `DELETE /installation/token` as soon as the clone ends, whether it succeeded or not. The token never leaves the agent's memory. The build context leaves out `.git`. Repository lists use a token with `metadata: read` and no repository filter, revoked the same way.
- **Fixed hosts.** The agent and the dashboard call only `https://api.github.com` and `https://github.com`, built from stored owners, names and ids, never from a URL in a webhook body or a request row, so ASVS v5.0.0-1.3.6 still holds.

### Webhooks, polling and the queue

- **The webhook endpoint.** `POST /api/github/webhook` is outside the session check, and is the only such route besides login and setup. The same-origin check still applies and passes, since GitHub sends JSON with no `Origin` header. It reads at most 1 MiB (push payloads list at most 20 commits, so a real one is far smaller), requires `X-GitHub-Event`, `X-GitHub-Delivery` and `X-Hub-Signature-256`, and answers `204` without asking `tero-keys` for events it doesn't handle. For `ping`, `push`, `installation` and `installation_repositories` it sends the raw body and signature to `tero-keys` in `github.webhook.verify`, which answers only valid or invalid, comparing in constant time. Invalid signatures answer `401`, are charged to a per-IP throttle (10 a minute, then `429` without asking `tero-keys`) and recorded as `webhook_signature_failed`, which a flood can prune. Delivery ids handled in the last 3 days, GitHub's redelivery window, are kept in the database, and a repeat is answered `200` and ignored. The signature covers only the body, so a captured delivery sent again with a new id is accepted; it can only queue a deploy of the branch head, which a push would have done anyway. The secret stays in `tero-keys` because a leaked secret would let anyone trigger builds from outside long after a breach is fixed.
- **A push is a trigger, never a commit.** A verified `push` is matched to apps by the repository's GitHub id and the branch in `ref`. Branch deletions (`deleted: true`) and tags queue nothing. The deploy records the pusher's login and the pushed SHA for display, but the agent still clones the branch head it reads from GitHub. If the head is newer by then, it deploys the newer commit; if it isn't the pushed commit (a force-push back, a forged delivery), it deploys the head anyway. A webhook can therefore only ever cause a deploy of what the branch really points at.
- **Deploy on push, per app.** Each app has a "Deploy on push" setting, on by default. Off, pushes, polls and redeliveries queue nothing for that app, and Redeploy still works.
- **Apps remember the repository's id.** An app created from the installation's repository list stores the GitHub repository id next to its owner and name, and matches pushes by id. A rename or transfer keeps working; the stored name is refreshed from the next verified push. An app created from a public URL stores the id too when the installation covers that repository, and switches to webhooks from then on.
- **Polling public repositories.** Every minute, the agent lists the refs of each public app's repository that the installation doesn't cover (the same ref listing slice 2 uses for the default branch, on `github.com` only, with no credential), with up to 10 seconds of jitter per app. When the tracked branch's head differs from the commit of the app's newest deploy, it queues one with trigger `poll`. A repository that is missing or has gone private stops being polled after 3 failures in a row and the app page says why; Redeploy or a successful poll after the admin fixes it resumes it. Polling sits in the agent so that every outbound call to GitHub comes from one process.
- **Missed webhooks redelivered at start.** When the agent starts with GitHub connected, it lists the App's recent deliveries (`GET /app/hook/deliveries`) back to the oldest it hasn't seen, and asks GitHub to redeliver (`POST /app/hook/deliveries/{id}/attempts`) each failed `push`, `installation` or `installation_repositories` delivery whose id Tero hasn't handled, once per id. This is what GitHub's docs recommend. The redelivery arrives signed through the normal endpoint, so nothing about it is trusted that a live delivery isn't. Several missed pushes to one app collapse into one queued deploy of the head. A delivery that fails while Tero is running isn't retried; GitHub's App page shows it, and Redeploy deploys the head. Vercel and Railway don't recover missed pushes either, as far as their public forums show.
- **The per-app queue.** An app holds at most one deploy building or starting and at most one queued, enforced by two partial unique indexes. Any trigger while the app has a queued deploy updates that row's trigger, pusher and requested SHA instead of adding one; since the agent resolves the head when it starts, the queued deploy builds the newest commit either way. A trigger while a deploy is building or starting queues one behind it. Redeploy is therefore always accepted; the button reads "Queued" while a deploy waits. Builds stay one at a time across the server, oldest queued first.
- **Triggers.** `deploys.trigger` is one of `create`, `manual`, `push` or `poll`, with the pusher's login for `push`. The app page shows it next to each deploy. Slice 7 builds its history on it.

### Disconnect, rotation and breach

- **Disconnect.** The GitHub section shows the App's name, the account it is installed on and the repositories it covers, with **Disconnect** (confirmed session). Disconnecting deletes the `github_app` row in `tero-keys`, and the installation and its repository list in the database. Every app is unlinked from its repository id, so apps from public repositories go back to polling; a deploy of a private one fails with "That repository wasn't found... connect GitHub in Settings", and polling stops after 3 tries with that reason on the app page. A refresh that finds a repository no longer covered unlinks its apps the same way, and connecting again links them back by owner and name. GitHub has no API to delete an App with its own credentials, so the page links to the App's settings on GitHub to delete it there. Connecting again creates a new App, and apps find their repositories again by id.
- **Rotation.** `key.rotate` re-seals the App's private key and webhook secret. `login.reset` doesn't touch the connection, so `reset-login` keeps deploys working.
- **Breach.** `assume-breach` also stops `tero-agent`'s user manager and every process running as `tero-agent`, moves aside each user's whole `~/.config` (units, `environment.d`, `user.conf`, Podman's `containers.conf`, registries and policies) and Podman's quadlet directory, and any crontab, removes BuildKit's cache volume and image once the user manager is back, says to redeploy every app so images are rebuilt from source, and deletes the GitHub connection (root verb `github.forget`). The shared database's apps and deploys are left as they are; the admin sees them in the dashboard. Its output adds "Delete the GitHub App `<name>` at its settings page on GitHub, then connect GitHub again". The private key never passes through the dashboard now, but a compromised agent could have read it during the conversion or minted tokens, and security comes first.

### Verbs, events and tests

- **Verbs.**
  - dashboard: `github.connect.begin` (confirmed session), `github.connect.approve` (the session that began it), `github.disconnect` (confirmed session), `github.status` (App id, slug, owner, never the secrets), `github.webhook.verify`, plus slice 4's verbs
  - agent: `github.connect` (an approved, unused state), `github.status`, `github.jwt`
  - root: `github.forget`, `github.status`, plus slice 4's verbs
  The protocol's message cap rises from 128 KiB to 2 MiB, so a 1 MiB webhook body fits base64-encoded.
  No verb returns the private key or the webhook secret, and only the agent gets a JWT.
- **Events.** `tero-keys` records `github_connected` and `github_disconnected` (both kept through a flood) and `webhook_signature_failed` with the sender's IP (prunable). The dashboard appends `github_installation_changed` when a verified `installation` or `installation_repositories` webhook arrives, and asks the agent to refresh. Pushes and polls aren't security events; they show as deploys.
- **Testing.** e2e builds compile in a fake GitHub, like Pebble for ACME: it serves the manifest form and conversion (personal and organization), App and installation endpoints, deliveries and redelivery, the fixtures over git's smart HTTP (public and private), and a helper that sends signed webhooks to the server. It records token revocations, so tests can check every token was revoked. Release builds can't reach it. Before the release, one manual run on a cloud server against real GitHub with a test account and a test organization covers what the fake can't: GitHub's own pages, its redirects and real deliveries.

## Risks / Trade-offs

- [The agent move touches slice 2's foundations] → Podman's owner, the subordinate range, linger, paths and the database's location all change. Slices 1 to 4's e2e suites run again on both releases and architectures, and there are no installs to migrate.
- [Two users share the database] → Either can write any row, as when both were `tero`. The agent keeps re-validating every field, and the dashboard can still only queue deploys of existing apps, which it could already do. Group permissions on SQLite's WAL and shared-memory files are checked on both tested releases in part 1.
- [A compromised agent can read every covered repository] → It holds `github.jwt` while compromised. It listens on nothing, its inputs are database rows and GitHub's answers, and `assume-breach` deletes the connection. The App is read-only and the admin chooses its repositories.
- [Dashboard-to-agent requests add latency] → Connecting and private branch checks wait for the agent's one-second poll. A few seconds once per app creation; the form says when it's waiting.
- [Webhook bodies reach `tero-keys`] → `tero-keys` only computes an HMAC over bytes capped at 1 MiB, never parses them, and only after the dashboard checked the headers and the throttle. Raising the message cap to 2 MiB lets a caller make `tero-keys` hold more memory per connection; connections are capped per caller, and a dashboard able to send them could already keep it busy hashing passwords.
- [Untrusted input reaches processes running as `tero-agent`] → pasta or slirp4netns and rootlessport run as `tero-agent` and carry the apps' traffic, and `tero-keys` trusts that uid for `github.jwt`. A bug in one of them would reach the App's tokens. A later slice could run Podman's helpers under a uid apart from the agent's.
- [Both users can create files in the shared directory] → The build logs' directory belongs to `tero-agent` and is only readable by the group, and the database refuses to open through a link, so neither user can make the other write where a link points.
- [Polling costs requests] → One small ref listing per public app per minute, which GitHub doesn't count against the REST limit, and a page or two of deliveries when the agent starts.
- [A delivery lost while Tero runs stays lost] → Rare (a network blip, a timeout), visible on the App's page on GitHub, and fixed with Redeploy.
- [The webhook URL is the dashboard domain] → GitHub must reach it, which needs ports 80 and 443 open (slice 1's reachability check). A `nip.io` dashboard works; the private-access ideas after v1 would need the webhook route exempted.
- [GitHub's pages and redirects can change] → The manual run against real GitHub before each release catches it; the fake only proves Tero's side.
