## Context

Slice 2 runs two long-lived processes as the `tero` user: `tero serve` (dashboard, API and Caddy) as the system unit `tero.service` with a tight sandbox, and `tero agent` as a user unit under `tero`'s user manager with no sandbox, because rootless Podman breaks under every systemd sandbox option. They share one SQLite database, which today also holds the admin's password hash, the TOTP secret in clear, the setup links and the security events.

ADR 0001 section 5 plans a 256-bit key-encryption key (KEK) sealed with `systemd-creds` and delivered with `LoadCredentialEncrypted=`, envelope encryption of app secrets and `sudo tero rotate-key`. None of it is built.

Facts that decide the design:

- `systemd-creds --user`, which lets a user unit receive an encrypted credential, arrived in systemd 256. Ubuntu 24.04 ships 255 and 26.04 ships 259. System units have had `LoadCredentialEncrypted=` since 250.
- `tero serve` and `tero agent` share a uid. `user@.service` delegates its cgroup subtree to `tero`, so any process running as `tero` under the user manager (conmon, pasta, slirp4netns, an SSH session as `tero`) can move itself into `tero-agent.service`'s cgroup or replace the unit from `tero`'s own config directory. Only the dashboard is fenced off from that, by `ProtectHome=yes` and `ProtectControlGroups=yes`.
- A credential `LoadCredentialEncrypted=` can't decrypt fails the unit's start (status 243/CREDENTIALS). Files loaded from a directory get the credential name `<id>_<file name>`, and that name must match the one embedded at encryption.

## Goals / Non-Goals

**Goals:**
- The dashboard can't read the KEK, the TOTP secret or the password hash, and can't replace the admin's credentials: after the bug that let an attacker into the dashboard is fixed and `assume-breach` has run, the attacker has nothing left that logs in.
- No process running as `tero` can read the KEK, read a TOTP secret at rest, or change a recorded security event.
- A lost or unreadable key never takes apps offline.
- One command for a suspected breach.
- Identical design on Ubuntu 24.04 and 26.04, amd64 and arm64.

**Non-Goals:**
- App secrets and environment variables (slice 6). How the agent gets app secrets is decided there. The agent isn't a caller of `tero-keys` in this slice, because it can't yet be told apart from other processes running as `tero`, and because the dashboard writes the deploy rows the agent acts on, so a compromised dashboard could steer it.
- Moving sessions out of the dashboard. A compromised dashboard can create sessions in its own database; `assume-breach` deletes them all.
- Shipping logs off the server (ASVS 16.4.3 stays a gap).
- Protecting against root on the host or the hosting provider.
- Password change and the session list (slice 4).

## Decisions

- **A third process with its own user.** `tero keys` (same binary) runs as `tero-keys.service`, `User=tero-keys`, a system user with no shell, no password and no group shared with `tero`. It doesn't run Podman, so it gets the full sandbox: `PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`, an empty `CapabilityBoundingSet=`, `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateDevices`, `PrivateTmp`, `MemoryDenyWriteExecute`, `SystemCallFilter=@system-service`, `SystemCallArchitectures=native`, `LimitCORE=0`, `UMask=0077`, `MemoryMax=256M` (two Argon2id hashes of 64 MiB at a time), `StateDirectory=tero-keys` (0700). It doesn't set `ProtectProc=`, because it reads other processes' cgroups. A different uid means the kernel keeps `tero` out of its memory, files and credential directory.
- **Why not the agent or the dashboard.** The agent can't receive a sealed credential on systemd 255, and anything running as `tero` under the user manager can pose as it. The dashboard is the process an attacker reaches first.
- **Socket activation.** `tero-keys.socket` creates `/run/tero-keys/keys.sock` with `SocketUser=tero-keys`, `SocketGroup=tero`, `SocketMode=0660`, `DirectoryMode=0755`. systemd, as root, can give the socket the `tero` group, which `tero-keys` itself can't. Connections made while `tero-keys` restarts wait in the socket's queue instead of failing.
- **The dashboard only wants `tero-keys`.** `tero.service` has `Wants=` and `After=tero-keys.socket`, not `Requires=`, so restarting or failing `tero-keys` never stops the dashboard or Caddy, and apps keep serving. Login fails closed while `tero-keys` can't answer.
- **The sealed key.** Init generates the KEK with `crypto/rand` and seals it with `systemd-creds encrypt --with-key=auto --tpm2-pcrs= --name=kek_<version>` into `/etc/tero/keys/<version>`: TPM2 plus the host key when a TPM2 is present, the host key in `/var/lib/systemd/credential.secret` otherwise, and no PCR policy, so kernel and firmware updates don't lock it. A new file is written to `/etc/tero/keys.new/`, synced, then renamed into `/etc/tero/keys/`, so the directory never holds a partial file. The unit loads `LoadCredentialEncrypted=kek:/etc/tero/keys/`, which gives `tero-keys` `$CREDENTIALS_DIRECTORY/kek_<version>` for every version on disk. A version number is never used twice: the next one is one past every version in `/etc/tero/keys/` and `/etc/tero/keys-unreadable/`, so a value sealed with a lost key is reported as such instead of failing to open under a new key with the same number.
- **A key that won't open.** If any file fails to decrypt (a cleared TPM, a disk moved to another server), systemd doesn't start `tero-keys`. Apps and the dashboard keep running; login and setup say the key service isn't running and to run `sudo tero reset-login`. `reset-login` sees `tero-keys`'s last run ended with status 243 (systemd reports `start-limit-hit` instead of `exit-code` after repeated failed starts, so only the status counts), moves the unreadable files to `/etc/tero/keys-unreadable/<time>/` (kept, never deleted), seals a new KEK and starts a fresh setup. Only the admin's credentials depend on the KEK in this slice, and `reset-login` replaces them anyway.
- **Callers are known at connect time.** On each connection `tero-keys` reads the peer's uid from `SO_PEERCRED`, which records the credentials at `connect()`, so a process that later execs a setuid program doesn't change it. uid 0 is root. For uid `tero` it takes a pidfd for the peer (`SO_PEERPIDFD`, Linux 6.5), reads that process's cgroup, then checks the pidfd still refers to a running process so a recycled pid can't pass. Only the exact cgroup path `/system.slice/tero.service` is the dashboard. Everything else is refused, and refusals are counted, not logged one by one (see the log limits).
- **A small, fixed protocol.** One request per connection: a 4-byte length, then JSON `{"verb": ..., "args": {...}}`; one answer in the same form. Requests over 64 KiB are refused, a connection that sends nothing for 5 seconds is closed, and at most 32 connections per caller are served at once. The caller is identified before it takes a connection, from what the kernel recorded, so a flood from the dashboard can't keep root's commands out and refused callers never hold one. Verbs by caller:
  - dashboard: `setup.begin`, `setup.finish`, `login.check`, `events.append`, `events.list`, `status`
  - root: `setup.issue`, `login.reset`, `key.rotate`, `events.append`, `status`
  No verb returns the KEK, the password hash or a stored TOTP secret.
- **The admin's credentials live in `tero-keys`.** Its database holds the one admin row (Argon2id password hash, TOTP secret sealed with the KEK, last used TOTP step) and the setup links (token hashes, expiry, the pending password hash and sealed pending TOTP secret).
  - `setup.issue` (root) replaces any unused link and returns a new token. Only root can issue one.
  - `setup.begin` (dashboard) takes a token and a password the dashboard has already checked against the length, blocklist and breach rules, which need the network `tero-keys` doesn't have. It refuses unless the token is valid and no admin exists, then hashes the password, creates a TOTP secret, stores both as pending on the link and returns the `otpauth://` URI and secret once, for the QR code.
  - `setup.finish` (dashboard) checks a code against the pending secret and, in one transaction, creates the admin and uses up the link.
  - `login.check` (dashboard) takes a password and a code, checks both, always doing the Argon2id work so timing doesn't say which factor failed, keeps slice 1's single-use rule and ±30 s drift, and answers pass or fail.
  - `login.reset` (root) deletes the admin and every link.
  A compromised dashboard therefore can't set a password, enrol a TOTP secret, or reuse one, and the setup state is in one database, so there is no half-finished setup across two.
- **Sealed values are tied to their row.** AES-256-GCM with a fresh 96-bit nonce; the additional data is the table, column, row key and KEK version, so a ciphertext copied to another row or relabelled with another version doesn't open.
- **Throttling stays in the dashboard, with a backstop in `tero-keys`.** The dashboard keeps slice 1's per-IP, per-device and per-account limits and calls `login.check` only for attempts that pass them. `tero-keys` adds its own limit that the dashboard can't bypass: when 20 checks in 24 hours have the right password and a wrong code, it refuses `login.check` for 24 hours and records `totp_locked`. Every such failure is recorded as `totp_failed`, since it means someone has the password. Wrong passwords don't count toward that limit, so strangers can't lock the admin out, and they are throttled by the dashboard as today. At 20 guesses a day with three valid codes each, a compromised dashboard needs about 45 years on average to guess a code.
- **Security events live in `tero-keys`.** Its database has the only `security_events` table. `tero-keys` records the login and setup events itself. Callers may append the few events only they can see (`rate_limited`, `breach_check_skipped`) with a source IP and no free text. `tero-keys` adds the time and the caller, which the caller can't choose. Each event is also written to the journal from `tero-keys.service`, so the trusted field `_SYSTEMD_UNIT=tero-keys.service` marks the genuine copy; `tero` isn't in `systemd-journal` and can't change the journal. Limits: 60 appended events per caller per minute, beyond which `tero-keys` keeps one `events_dropped` event with a count per minute, refused connections counted the same way as `callers_refused`, and at most 100,000 rows, oldest pruned first, except `login_succeeded`, `setup_completed`, `login_reset`, `key_rotated`, `breach_reset` and `totp_locked`, which a flood of other events can't push out. Events are kept one year.
- **When `tero-keys` can't be reached.** Login and setup fail with "the server's key service isn't running" before any session is created. An event the dashboard can't append goes to its own journal output with `TERO_EVENT_UNSTORED=1`, so it isn't lost.
- **The dashboard's own database.** It keeps sessions, trusted browsers and login throttles. Root commands still open it through the `_login-link` child running as `tero`; the root parent is the one that talks to `tero-keys`. `tero.service` gets `LogRateLimitIntervalSec=30s` and `LogRateLimitBurst=1000`, so it can't flood the journal into rotating out older entries.
- **Failures that say nothing about the credentials are taken back one by one.** When the key service is down, busy, locked or the setup link is invalid, the dashboard takes back only that attempt's charge to its throttle and keeps any lockout, so such requests can't clear the counters other attempts built up.
- **The key service limits login checks itself.** Wrong passwords are throttled by the dashboard, which a compromised dashboard skips. So `tero-keys` answers at most 30 `login.check` requests per minute, whoever they are for, and counts the rest in one `rate_limited` event per minute. The dashboard's throttle stops browsers other than trusted ones after 10 failures for the account, so an attack from outside can't use the 30 up. The dashboard sees a wrong code with the right password listed as `login_failed`, like a wrong password: otherwise a compromised dashboard could read in `events.list` which password guess was right. Root and the journal see `totp_failed`. A wrong password makes the same database write a wrong code does, so timing doesn't tell them apart either. A login only succeeds in a statement that also checks the code lock, so checks that were hashing when the limit was reached can't pass.
- **Rotation keeps a key that opens every row at every step.** `sudo tero rotate-key` seals KEK version n+1 into `/etc/tero/keys/` (through `keys.new/`), restarts `tero-keys` so it holds both, sends `key.rotate`, which re-encrypts every sealed value with the newest key in one transaction, removes every older version's file and restarts `tero-keys` again. A crash at any point leaves files that open every row, because each row names its version and a file is only removed after no row names it. `key.rotate` refuses while any row still names a version that isn't loaded.
- **`sudo tero assume-breach`.** Lists what it will do and asks the admin to type `yes` (`--yes` for scripts). Then: stops `tero.service`, so no code an attacker left in the dashboard's memory survives and nothing re-creates sessions while the rest runs; stops `user-<uid>.slice` (the user manager with the agent, builds and apps, and every session, cron jobs included) and `user-runtime-dir@<uid>.service` (`/run/user/<uid>`); moves `tero`'s crontab aside; kills any process still running as `tero` and checks with `pgrep` that none is left (only its "no match" exit counts), so nothing can write a session into `tero.db` once the reset is done; then moves aside the user unit directories Tero never uses (`~/.config/systemd/user`, `~/.config/systemd/user.control`, `~/.local/share/systemd/user`, `~/.config/containers/systemd`). Each path is checked part by part with `lstat`, and the first part that isn't a real directory is moved itself, so a planted link is moved as a link and never what it points to. Everything goes to `/var/lib/tero-breach/<time>-<random>/`, readable only by root; deletes every session, trusted browser and throttle; deletes Caddy's stored certificates, private keys and ACME account, so new ones are issued; rotates the KEK; resets the login and issues a new setup link; records `breach_reset`; starts `tero`'s user manager, then `tero.service`. Apps are down until the agent starts them again, usually a few minutes, and the command says so before asking. It then prints the setup link and what to do outside the server: install the latest Tero if the cause may be a Tero bug, change the password anywhere it was reused, remove the old Tero entry from the authenticator app, check SSH's authorized keys, and each file it moved aside. Slices 5 and 6 add the GitHub App and each app's secrets to that list.
- **What rotation doesn't cover.** Without a TPM, the KEK is sealed with the host key, which sits on the same disk. Someone holding a full-disk copy can open every KEK sealed with that host key, including ones made after the copy. `assume-breach` says so on servers without a TPM. Replacing the host key is left out: other services on the server may have credentials sealed with it.

## Risks / Trade-offs

- [`tero-keys` is down] → Login and setup fail closed; existing sessions keep working and apps keep serving. systemd restarts it, and init checks it answers `status` before printing the setup link.
- [A TPM-bound key is lost with the TPM] → `reset-login` recovers, and the unreadable files are kept.
- [Without a TPM, the host key is on the same disk] → See "What rotation doesn't cover". ASVS 13.3.3 is met only on servers with a TPM2, and the ASVS document says so.
- [Anything running as `tero` can create sessions in `tero.db`] → The dashboard, the agent, builds that reach uid `tero` and planted user units can all write the database, so they can give themselves a dashboard session without the key service. `assume-breach` stops every `tero` process before it deletes sessions. Moving sessions into `tero-keys` would close this; it puts the socket on every request.
- [The dashboard sees the password and TOTP secret during setup] → Unavoidable: it receives the form and draws the QR code. `assume-breach` stops the dashboard before issuing the new link.
- [Argon2id runs in `tero-keys`] → Two hashes at a time, as today, within its memory limit; the dashboard's throttling runs first, and the key service checks at most 30 logins a minute.
- [A compromised dashboard still guesses passwords at 30 a minute] → About 43,000 guesses a day. The password policy (blocklist and breach check) and TOTP behind it are what hold; the code guessing limit stops it at the second factor.
