## Context

After slice 3, `tero-keys` holds the admin's password hash, the sealed TOTP secret, setup links, the code guessing limit and the security log. The dashboard (`tero serve`, `tero.service`) keeps sessions, trusted browsers and login throttles in `tero`'s SQLite database and asks `tero-keys` only `login.check`: pass or fail. Anything running as `tero` can write that database, so it can insert a session row and use the dashboard without ever passing a login.

The dashboard has no settings page. Its API is JSON only, same-origin, with `SameSite=Strict` cookies; sessions last 30 idle minutes and 12 hours at most.

Facts that decide the design:

- WebAuthn verification needs no network when attestation is `none`: the browser's answer is checked against the stored public key, the challenge, the relying party ID and the origin. So `tero-keys` can verify passkeys inside its sandbox.
- A passkey is bound to its relying party ID, which must be the dashboard's domain or a parent of it. The dashboard domain can't change after `sudo tero init` in v1.
- ASVS 5.0.0 7.5.1 asks for full re-authentication before changing anything that affects authentication; 7.5.2 for at least one factor before ending sessions; 7.4.3 for the option to end other sessions after any factor is changed or removed.

## Goals / Non-Goals

**Goals:**
- Only `tero-keys` creates a session, and only after it checked a password and TOTP code, a passkey, or a setup link's code itself.
- The admin changes their password, sees and ends sessions, and manages passkeys from the dashboard.
- Passkey login works alone, and password with TOTP always stays as the fallback.
- No request that reads or changes the account works without a live session, even from the dashboard's own process.

**Non-Goals:**
- Recovery codes, email, or any other way back in than `sudo tero reset-login`.
- Changing the TOTP secret from the dashboard. `reset-login` re-enrols it; a "replace authenticator" flow can come later.
- Turning off password and TOTP for passkey-only accounts.
- Attestation or an allowlist of authenticator models.
- Protecting a live session from a compromised dashboard: while compromised, it sees every cookie and request. What this slice removes is persistence after the bug is fixed.

## Decisions

- **Sessions, trusted browsers and throttles move to `tero-keys`.** Its database gains `sessions`, `trusted_devices` and `login_throttles`, with the same rules as slice 1 (30 idle minutes, 12 hours, 180-day devices, the per-IP, per-device and per-account lockouts). `tero`'s database keeps only apps, deploys and served routes, and its `0001_dashboard_access.sql` is removed. Throttles move with sessions because a login is now one request to `tero-keys` that checks the throttle, the credentials and creates the session in one place; leaving the throttle in the dashboard would mean two round trips and two databases to keep in step. The client IP still comes from the dashboard, which is the only process that sees the TCP peer; a compromised dashboard can lie about it, which the global 30-checks-a-minute limit and the code guessing limit already cover. Anything that isn't an IP address shares one throttle key, so made-up values can't add a row each.
- **Login is one request.** `login.password` takes the IP, the device cookie, the user agent, the password and the code, and answers with a new session token and device token, or the same errors as today. `setup.finish` answers with a session the same way. The dashboard sets the cookies and never sees a session row.
- **Every request checks the session in `tero-keys`.** `session.check` takes the cookie's token and answers the session's id and whether it is confirmed (see below), or that it has ended. It updates the last-used time and IP at most once a minute, so most checks only read. It is one Unix-socket round trip per API request; the dashboard makes few requests, and revocation takes effect at once, which a cache would lose. `/api/state` uses the same call, which also says whether the login is set up.
- **Account requests carry the session.** `session.list`, `session.revoke`, `account.confirm`, `password.change`, the `passkey.*` verbs and `events.list` all take the caller's session token and fail unless it is live. A compromised dashboard can only act on the account while it holds a token a browser sent it; it can't list sessions, read events or add a passkey on its own.
- **Sessions are listed by id, never by token.** Each session gets a random 128-bit id at creation, which the list shows and `session.revoke` takes. The token hash never leaves `tero-keys`.
- **What the session list shows.** Start time, last-used time, the IP at login and the latest IP, the user agent (cut to 256 bytes), how it logged in (password and TOTP, passkey, or setup) and which entry is this browser. The page shows a short "Firefox on macOS" label it derives from the user agent, and the full string when it can't. Ending the current session is logging out; "End all other sessions" keeps the current one.
- **Confirming it's you.** `account.confirm` takes the password and a TOTP code and, when both pass, marks the session confirmed for 5 minutes (`confirmed_at` on the session row). A login or setup with the password and a code is the same check, so the session it starts is confirmed from the start; a passkey login isn't. Ending sessions and adding, renaming or removing a passkey need a confirmed session. The settings page shows every action; when one is refused for want of confirmation, which the dashboard marks with the code `not_confirmed` so no other 403 is mistaken for it, it asks for the password and code and then carries the action out. Other actions wait while the form is open. Adding a passkey is the exception: browsers such as Safari only open the passkey prompt right after a click, so once confirmed the page asks the admin to press **Add a passkey** again. A login or setup with the password and a code confirms; every other method, passkeys included, doesn't, so a method added later starts unconfirmed.
- **Passkey offered after login.** After a login or setup with the password and a code, when the admin has no passkey, the dashboard shows "Log in faster next time" with **Add a passkey** and **Not now** before the page the admin was going to. The login just confirmed the session, so adding one asks for nothing more. "Not now" is kept in the browser's local storage, so each browser asks once; nothing about it is on the server. Confirmation is always password and TOTP, not a passkey: the roadmap asks for that before adding a passkey, and one rule for every action is easier to reason about. Wrong confirmations are charged to the same throttles as logins (device or account, and IP) and to the code guessing limit, so a stolen session can't guess the password faster than the login page allows. A code used to confirm can't be used again, like a login code.
- **Password change.** One form: current password, TOTP code, new password, and "End every other session" (checked by default). `password.change` checks the current password and code like a confirmation, then stores the new hash, all in `tero-keys`. The dashboard first runs the length, blocklist, breach and context-word checks on the new password, as it does at setup, since the breach check needs the network `tero-keys` doesn't have. Passkeys and the TOTP secret are kept. ASVS 6.2.3 asks for the current password in the change itself, which is why this form doesn't rely on the confirmation window.
- **Context words.** A new password is refused when it contains, ignoring case, "tero", "admin", the dashboard domain, any label of the dashboard domain that is at least 4 characters and not all digits, or the server's public IP. For `deploy.example.com` that is "tero", "admin", "deploy.example.com", "deploy" and "example". The check runs in the dashboard's password policy, so setup and password change share it, and the error names the word found.
- **Passkeys are verified in `tero-keys`.** It uses `go-webauthn/webauthn` with the relying party ID set to the dashboard domain and the origin `https://<domain>`, both read from `/etc/tero/config.json` at start, so a compromised dashboard can't make it accept a passkey made for another site. Registration asks for a discoverable credential (resident key required), user verification required and attestation `none`, with ES256, EdDSA and RS256. The admin row gets a random 32-byte WebAuthn user handle; `login.reset` replaces it, so passkeys left on an authenticator after a reset no longer match.
- **Challenges live in memory in `tero-keys`.** `passkey.register.begin` and `login.passkey.begin` return options with a fresh 32-byte challenge, kept with its kind, the session it belongs to (for registration) and a 2-minute expiry. Each challenge works once. At most 1,024 login challenges are open at a time and at most 4 per IP (or IPv6 /64), oldest dropped first, so an unauthenticated flood of "begin" requests costs only capped memory and needs many addresses to push out the admin's challenge. A restart forgets them, which only fails ceremonies in progress.
- **Passkey login.** The login page offers "Log in with a passkey" next to the password form, through a usernameless request. `login.passkey.finish` takes the IP, the device cookie, the user agent, the challenge id and the browser's answer; it checks the signature, the user handle, user verification and the signature counter, then creates a session with method `passkey`. A failed assertion is charged to the IP throttle only: a signature can't be guessed, and charging the account would let strangers lock the admin out. An answer for a challenge that is gone or expired isn't charged at all, so a flood that pushes out the admin's challenge can't lock out the admin's IP. Passkey answers are capped at 30 a minute, counted apart from password checks. A counter that goes backwards (when the authenticator keeps one) fails the login and records `passkey_counter_mismatch`.
- **Managing passkeys.** At most 10. The admin names each one when adding it (1 to 64 characters, default "Passkey"), can rename it, and sees when it was added and last used. Adding and removing need a confirmed session and offer "End every other session" (checked by default), as ASVS 7.4.3 asks. Removing the last passkey is allowed, since password and TOTP remain.
- **Passkeys and the master key.** Passkey public keys aren't secret and are stored in clear, tied to the admin. Nothing new is sealed with the master key, so `key.rotate` doesn't change.
- **Reset and breach.** `login.reset` deletes the admin, setup links, sessions, trusted browsers, throttles, passkeys and the code guessing state in one transaction. `reset-login` and `assume-breach` no longer open `tero`'s database, so the `_login-link` child goes away. `assume-breach` still stops every process running as `tero` before the reset, so nothing an attacker left behind is running when the new setup link is issued, and its output adds "remove the old Tero passkeys from your devices".
- **Verbs by caller.**
  - dashboard: `status`, `setup.begin`, `setup.finish`, `login.password`, `login.passkey.begin`, `login.passkey.finish`, `session.check`, `session.end`, `session.list`, `session.revoke`, `account.confirm`, `password.change`, `passkey.register.begin`, `passkey.register.finish`, `passkey.list`, `passkey.rename`, `passkey.remove`, `events.append`, `events.list`
  - root: `status`, `setup.issue`, `login.reset`, `key.rotate`, `events.append`, `events.list`
  `login.check` goes away. No verb returns a session token except the three that create a session, and none returns a token hash, the password hash, the TOTP secret or the master key.
- **Events.** `tero-keys` records `password_changed`, `account_confirmed`, `confirm_failed`, `sessions_ended` (with the count), `passkey_added`, `passkey_removed`, `passkey_login_succeeded`, `passkey_login_failed` and `passkey_counter_mismatch`. A wrong code on confirmation or password change is recorded as `confirm_totp_failed` and shown to the dashboard as `confirm_failed`, for the same reason slice 3 shows a wrong login code as `login_failed`. `passkey_login_succeeded`, `password_changed`, `passkey_added` and `passkey_removed` join the events a flood can't prune. The dashboard no longer appends `rate_limited`: the throttles are in `tero-keys`, which records it itself.

## Risks / Trade-offs

- [`tero-keys` down means no dashboard at all] → Before, existing sessions kept working while it was down; now every page needs it. Apps keep serving, systemd restarts it, and the page says the key service isn't running. This is the cost of sessions nobody else can create.
- [One socket round trip per request] → Small next to the request itself; the last-used write happens at most once a minute.
- [A compromised dashboard sees session tokens in flight] → It can act as the admin until those sessions end. `assume-breach` ends them all; the admin can also end them from the list once the bug is fixed.
- [A compromised dashboard can add its own passkey] → During the 5 minutes after the admin confirms, it can register a key it holds with the admin's session, and that key outlives a password change. The passkey list shows every key with its name and date, `passkey_added` is a warning in the journal, and `assume-breach` deletes them all.
- [New dependency in the key service] → `go-webauthn/webauthn` is the common Go implementation and needs nothing at runtime; it runs only on requests that already passed the caller check.
- [The confirmation window lets a stolen session act for 5 minutes] → Only on a session that just proved the password and a code, and only ending sessions or managing passkeys; password change always asks again.

## Open Questions

- Should a passkey also be accepted to confirm (for ending sessions and removing passkeys), so passkey-first admins rarely type the password? The draft says no, to keep one rule; easy to add later.
