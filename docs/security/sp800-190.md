# NIST SP 800-190 for builds and app containers

Builds and apps run in rootless Podman under the `tero` user, driven by `tero agent`. They follow the countermeasures in section 4 of [NIST SP 800-190](https://csrc.nist.gov/pubs/sp/800/190/final), Application Container Security Guide. CIS covers the host Tero runs on ([cis-subset.md](cis-subset.md)); SP 800-190 covers what runs in containers on it. ADR 0001 section 3 sets the container rules.

The document's terms map onto Tero like this:

| SP 800-190 | Tero |
|---|---|
| Image | The image Railpack plans and a throwaway rootless BuildKit builds for each deploy, plus the BuildKit image itself |
| Registry | None. Images are loaded straight into `tero`'s Podman store and never pushed anywhere |
| Orchestrator | `tero agent`, which runs every build and every Podman call, and the dashboard, which records the deploys the agent runs |
| Container | One container per deploy, `tero-app-<name>-<deploy>` |
| Host OS | A supported Ubuntu, hardened by `sudo tero init` |

The end-to-end suite checks the rows that name a test. Subtests are in `e2e/deploy_test.go` and `e2e/init_test.go`.

## Status values

| Status | Meaning |
|---|---|
| Done | Tero applies the countermeasure today. |
| Partly | Part of it is applied; the row says what is missing. |
| Later | Applies once a feature from a later slice exists. The slice is named in the row. |
| Not yet | The countermeasure applies and no slice is assigned yet. |
| N/A | The risk doesn't exist in Tero, for the reason given. |

## Summary

Not done yet, in the order they matter most:

| Section | What is missing |
|---|---|
| 4.4.2 | Containers and builds can connect anywhere on the internet, including the cloud metadata service. Blocking the metadata addresses is on the roadmap (slice 1); the rest of the outbound policy is an open decision. |
| 4.4.3 | App containers have no memory, CPU or process limits and a writable root file system. Resource limits per app are an open decision. |
| 4.1.1, 4.1.3 | Built images aren't scanned for known vulnerabilities or malware. |

## Images (4.1)

| Section | Countermeasure | Status | How | Test |
|---|---|---|---|---|
| 4.1.1 | Find and fix vulnerabilities in images | Not yet | Every deploy builds from a fresh Railpack plan, so base layers are as recent as the Railpack version in the Tero release. Nothing scans the built image | — |
| 4.1.2 | Image configuration follows secure practice | Partly | Railpack writes the image configuration. Whatever user the image names, the container runs in a user namespace of its own, so its root is an unprivileged host uid | e2e `process-isolation: Container options / Apps run as different host uids / App port not exposed` |
| 4.1.3 | Find malware in images | Not yet | Builds run the admin's own repository code, inside BuildKit's sandbox in a rootless container | — |
| 4.1.4 | No secrets stored in images | Later | Apps have no secrets yet. Slice 6 keeps them out of images and logs; Railpack plans pass build secrets as BuildKit secret mounts, which don't end up in layers | — |
| 4.1.5 | Use only trusted images | Partly | The BuildKit image is pinned by digest. Railpack's builder and runtime images come from `ghcr.io` as the Railpack version in the release names them. App images exist only in `tero`'s Podman store under `localhost/tero/` | — |

## Registries (4.2)

| Section | Countermeasure | Status | How | Test |
|---|---|---|---|---|
| 4.2.1 | Connect to registries over encrypted channels | Done | Podman pulls the BuildKit image and Railpack's images over HTTPS from `docker.io` and `ghcr.io`. No image is pushed | — |
| 4.2.2 | Remove stale images | Done | A redeploy removes the old release's image once the new one is live. Image retention for rollback comes with slice 7 | e2e `deployments: Redeploy picks up a new commit / Successful deploy / Redeploy while deploying` |
| 4.2.3 | Authenticate and authorize registry access | N/A | No registry. The image store belongs to `tero`, and the dashboard's own process can't reach it (`InaccessiblePaths=`) | e2e `process-isolation: Service can't change the agent's setup` |

## Orchestrator (4.3)

| Section | Countermeasure | Status | How | Test |
|---|---|---|---|---|
| 4.3.1 | Limit administrative access | Done | One admin, through the dashboard with two factors ([asvs-l2.md](asvs-l2.md)). The dashboard can only record deploys; it never runs Podman. Root work exists only as `sudo tero ...` | e2e `process-isolation: Dashboard cannot trigger root work` |
| 4.3.2 | Protect the orchestrator from unauthorized access | Done | The agent listens on nothing, runs as `tero`, and treats every database field as untrusted: it checks app names, URLs, branches and folders again and passes them to Podman as arguments, never through a shell. Its unit file is owned by root | e2e `server-init: Agent running after init / process-isolation: Agent has no listener`, `process-isolation: Agent unit not writable by tero` |
| 4.3.3 | Separate network traffic between containers | Done | Each app container gets a network namespace of its own (pasta with `--no-map-gw` on Podman 5, slirp4netns with `allow_host_loopback=false` on Podman 4), with no route to the host's loopback where other apps' ports are published. Each app's port is published on `127.0.0.1` only, for the built-in proxy | e2e `process-isolation: Apps can't reach each other directly` |
| 4.3.4 | Separate workloads of different sensitivity | N/A | One admin's apps on one server, all at the same trust level. BuildKit runs in its own range of subordinate ids, apart from every app | e2e `process-isolation: Container options / Apps run as different host uids / App port not exposed` |
| 4.3.5 | Trust between orchestrator nodes | N/A | One server. Multi-server is after v1 | — |

## Containers (4.4)

| Section | Countermeasure | Status | How | Test |
|---|---|---|---|---|
| 4.4.1 | Keep the container runtime free of known vulnerabilities | Done | Podman, its OCI runtime and its network helpers come from Ubuntu and get automatic security updates ([cis-subset.md](cis-subset.md)). The BuildKit image is pinned in the Tero release and updated with it | e2e `server-init: Automatic security updates` |
| 4.4.2 | Limit containers' outbound network access | Not yet | Outbound connections are open, so builds can reach the package registries they use. The cloud metadata block is on the roadmap (slice 1); the full outbound policy is an open decision on the roadmap | — |
| 4.4.3 | Secure container runtime settings | Partly | App containers: `--cap-drop=ALL`, `--security-opt no-new-privileges`, `--userns=auto`, never `--privileged`, no host network, no host folders, Podman's default seccomp profile, a size cap on logs. Missing: memory, CPU and process limits, and a read-only root file system. BuildKit runs with `seccomp=unconfined` and `unmask=/proc/*`, which it needs for its own sandbox; it applies its own seccomp profile to each build step and has a memory cap of half the server's memory, at least 1 GiB | e2e `process-isolation: Container options / Apps run as different host uids / App port not exposed`, `process-isolation: No container process owned by host root` |
| 4.4.4 | Find vulnerabilities in the apps themselves | N/A | The apps are the admin's own code; finding their bugs is the admin's job. Tero limits what a compromised app can reach (4.3.3, 4.4.3) | — |
| 4.4.5 | Prevent rogue containers | Partly | Only `tero` runs containers, and the dashboard's sandbox can't run Podman. The agent finds its containers by label, keeps each app's live deploy running, and removes leftover BuildKit and half-started containers. It doesn't remove containers it didn't start | e2e `deployments: Interrupted deploy`, `build-pipeline: BuildKit lifecycle / No published port or socket / Image available after build` |

## Host OS (4.5)

| Section | Countermeasure | Status | How | Test |
|---|---|---|---|---|
| 4.5.1 | Small host attack surface | Partly | Ubuntu, not a container-specific OS, so Tero runs on any VPS. Init disables unneeded services and opens only SSH, 80 and 443 ([cis-subset.md](cis-subset.md)) | e2e `server-init: Unneeded services and file permissions`, `server-init: Firewall default deny` |
| 4.5.2 | Group containers that share a kernel by sensitivity | Done | All apps on a server belong to one admin. Each runs as its own range of host uids | e2e `process-isolation: Container options / Apps run as different host uids / App port not exposed` |
| 4.5.3 | Keep host components updated | Done | Automatic security updates | e2e `server-init: Automatic security updates` |
| 4.5.4 | Limit who can log in to the host | Done | SSH keys only, no root login; `tero` and `tero-keys` can't log in; root is used only for `sudo tero` commands | e2e `server-init: SSH locked down`, `server-init: tero cannot log in interactively`, `server-init: tero-keys can't log in` |
| 4.5.5 | Protect the host file system from containers | Done | Containers get no host folders; BuildKit gets only its cache volume. auditd records changes to Tero's configuration and binary | e2e `server-init: Auditing and AppArmor` |
